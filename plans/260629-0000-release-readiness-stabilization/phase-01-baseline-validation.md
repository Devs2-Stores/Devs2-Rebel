# Phase 1: Baseline validation

## Overview

Establish a clean, reproducible baseline before changing behavior. This phase freezes the intended prune/migration scope and records the exact validation failures that later phases must close.

## Requirements

- Functional: identify which modified, deleted, renamed, and untracked runtime files are intentional.
- Functional: confirm active templates and section groups only point to sections that should remain active.
- Non-functional: do not change storefront behavior in this phase except documentation/status notes inside the plan if needed.
- Non-functional: keep findings grounded in command output or source reads, not assumptions.

## Architecture

The theme is a Shopify OS2.0 storefront where `layout/theme.liquid` composes global head snippets, section groups, global modals, and route-specific assets. Validation must cover the deployable theme surface, not only tracked files: Liquid sections/snippets/templates, JSON templates, assets, config, locales, CI workflow references, `.theme-check.yml`, and `.shopifyignore`.

## Implementation Steps

1. Capture `git status --short --untracked-files=all` and classify each runtime file as intended, accidental, or needs decision.
2. Capture `git diff --stat HEAD` and note high-risk modified areas: quickview, route CSS, contact/about, pruned sections, workflow/tooling.
3. Run `shopify theme check` and preserve exact errors/warnings.
4. Validate JSON templates after stripping Shopify autogenerated header comments.
5. Scan active `templates/*.json` and `sections/*-group.json` section types against existing active `sections/*.liquid` files.
6. Verify the BFL/newsletter workflow reference to `tools/generate_newsletter_image.py` against the current filesystem state.
7. Verify whether untracked `sections/main-search-quickview.liquid` and `templates/product.quickview.liquid` are intended active runtime files or accidental leftovers.
8. Produce a short baseline note: current blockers, intended prune state, and exact commands to rerun after fixes.

## Success Criteria

- [ ] Dirty working tree is classified into intentional vs unresolved changes.
- [ ] Active template/section references are known and any missing section references are listed.
- [ ] Current `theme check` output is captured.
- [ ] JSON template validation method is captured and repeatable.
- [ ] BFL workflow status is classified against the validated decision: disable/remove for this release unless the user explicitly reverses it.
- [ ] Quickview/search untracked files have an implementation decision before edits begin.
- [ ] Phase 2 has a concrete blocker list, not a vague cleanup list.

## Risk Assessment

Risk: changing files before understanding prune intent can reintroduce deleted sections or preserve accidental files. Mitigation: freeze scope first and only fix deployable active surfaces.

Risk: validation commands may be unavailable locally. Mitigation: record exact missing capability and use static checks as fallback, but do not mark release readiness complete without a real `shopify theme check` pass later.
